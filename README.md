# rate-limiting-patterns

[![CI](https://github.com/mohadjillani/rate-limiting-patterns/actions/workflows/ci.yml/badge.svg)](https://github.com/mohadjillani/rate-limiting-patterns/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Three rate-limiting algorithms behind one interface, each an atomic Redis Lua
script, with the two things that decide which one you want measured rather
than asserted — how much a client gets through by straddling a window
boundary, and what the strategy costs Redis.

Plus the question most implementations answer by accident, in a `catch` block:
what happens when Redis is down.

## The measurement

Generated by `npm run bench:accuracy && npm run bench:render`; full report and
method in [docs/bench/](docs/bench/README.md).

| strategy       | boundary overshoot | Redis commands | memory per client |
| -------------- | -----------------: | -------------: | ----------------: |
| `fixed-window` |          **2.00×** |              5 |              60 B |
| `sliding-log`  |          **1.00×** |              7 |           2,052 B |
| `token-bucket` |          **1.15×** |              5 |              93 B |

Overshoot is what one client gets through by spending its whole allowance just
before a window boundary and again just after. 1.00× is exact.

**The fixed window lets through twice the limit.** That is not a bug to tune
away — it is what a clock-aligned window means, and the only fix is a different
algorithm.

**The sliding log is exact and costs 34× the memory**, because it keeps one
sorted-set member per accepted request. That ratio grows with the limit: at
1,000 per minute it is 1,000 members per active client, not 100.

**The token bucket is the usual answer** — near-exact, memory like the fixed
window, and it lets an idle client spend a burst, which is what an API usually
wants. What it does not do is mean the same thing as "100 per minute": a bucket
of 100 refilling over a minute permits 100 in the first second and then a
trickle.

## Quick start

```bash
docker compose up -d redis     # or: redis-server
npm install
npm test                       # 48 tests, needs Redis
npm run bench:accuracy         # reproduces the table above
```

```ts
import { Redis } from 'ioredis';
import { TokenBucketLimiter, withDegradation } from 'rate-limiting-patterns';

const limiter = withDegradation(
  new TokenBucketLimiter(new Redis(), { limit: 100, windowMs: 60_000 }),
  { policy: 'open', onDegraded: (error) => metrics.increment('ratelimit.degraded') },
);

const decision = await limiter.consume(`user:${user.id}`);
if (!decision.allowed) return reply.code(429).send({ retryAfterMs: decision.retryAfterMs });
```

Or as Express middleware:

```ts
app.use(
  rateLimit({
    limiter,
    global: { limiter: globalLimiter },
    keyFor: (req) => req.user?.id ?? req.ip,
    costFor: (req) => (req.path.startsWith('/reports') ? 10 : 1),
  }),
);
```

## Why every decision is one Lua script

A decision reads a counter and writes it back. Done from the application, two
nodes read the same value and both write, and the limit is exceeded by however
many nodes were racing. More application code cannot fix it — the problem lives
in the gap between the read and the write.

Each strategy is therefore a single Lua script: one round trip, atomic by
construction. The test that pins this fires 200 simultaneous `consume` calls at
one key and asserts that **exactly** the limit is allowed — not approximately.

The scripts read the clock with Redis' `TIME` rather than the caller's.
Application nodes a few hundred milliseconds apart would otherwise disagree
about which window a request belongs to, and the limit would be enforced twice
at a boundary or not at all. One decision, one clock.

More in [ADR 1](docs/decisions/0001-lua-not-multi.md).

## When Redis is down

```ts
withDegradation(limiter, { policy: 'open' | 'closed' });
```

There is no default, because both are defensible and they are not
interchangeable. Fail open keeps the service up and unprotected — right when
the limit exists for fairness, wrong when it exists to stop abuse, since an
attacker who can take Redis down has also removed the limit. Fail closed lets
nothing through unmetered and turns a Redis outage into a full outage.

A circuit breaker sits in front. Without one, every request during an outage
waits for a connection timeout first, and a limiter that adds two seconds to
every request has taken the service down more effectively than the missing
limit would have. After a threshold of failures it stops calling Redis, then
lets exactly one request through per cooldown to test recovery.

Every degraded decision carries `degraded: true` and fires `onDegraded`,
because the failure that actually costs money is the silent one: a service
that has been unprotected for a week because failing open logged at debug
level. More in [ADR 2](docs/decisions/0002-fail-open-or-closed.md).

## Headers

`RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` on **every**
response, not only on the 429 — a client can only slow down before it is
refused if it is told where it stands while it is still being served. Plus
`Retry-After` on a 429, floored at one second, because `Retry-After: 0` invites
the immediate retry the limit exists to prevent.

No `X-` prefix: the IETF draft dropped it. [ADR 3](docs/decisions/0003-headers-on-every-response.md).

## Choosing

| you want                                          | use            |
| ------------------------------------------------- | -------------- |
| the cheapest thing that mostly works              | `fixed-window` |
| a hard contractual limit, and you have the memory | `sliding-log`  |
| an API limit that tolerates bursts                | `token-bucket` |

The overshoot number decides it. 2.00× is disqualifying for a limit that exists
to stop abuse and irrelevant for one that keeps a reporting endpoint from being
hammered. The benchmark says what each strategy does; it does not say which one
you need.

## Load scenarios

`bench/k6/` holds three profiles against the demo server — steady (the control,
below the limit), burst, and a burst straddling a boundary. They measure the
middleware under load rather than the strategies, and they are deliberately not
in CI: a load test on a shared runner measures the runner.

```bash
STRATEGY=token-bucket LIMIT=1000 WINDOW_MS=10000 npm run demo &
k6 run bench/k6/steady.js
```

Do not pass k6's `--vus` or `--duration` to the arrival-rate scenarios — they
replace the scenario with an open-throttle run, which turns the control into a
burst test. The numbers still come out; they measure something else.

## Limits

**Benchmarked on one machine, against a local Redis.** Latency is a floor, not
a capacity-planning number. The gaps being reported — 2× versus 1×, 60 bytes
versus 2 KB — are far larger than run-to-run variation, which is why a single
run supports them. A claim about a 5% difference would not be.
[bench/METHODOLOGY.md](bench/METHODOLOGY.md) states what is deliberately not
claimed.

**No distributed-quota coordination.** Every decision goes to one Redis. That is
the point — it is what makes the count correct — and it means Redis is in the
request path and is a single point of failure, which is why the degradation
policy exists. A design that gossips approximate quotas between nodes trades
correctness for that dependency; this one does not.

**Single Redis, not measured under failover or eviction.** Each decision uses
one key, so the strategies are cluster-safe by construction — but that is a
design property here, not a measured one.

**No sliding-window-counter strategy.** The approximation that interpolates
between two fixed windows is a genuinely good middle ground and is not
implemented; the token bucket occupies similar ground with simpler reasoning.
